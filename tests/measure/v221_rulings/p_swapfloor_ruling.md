### RR3. R4 is IN this ruling, not a separate item.

Measure on HEAD: `Close-grip bench press 3×12 → Dips → undo` leaves `3 sets — RPE 6 (…)` on the bench. That is V119's shape and it has been live since. R1 widens it from the unloadable pairs to all 38 movers, so it ships in the same build:

- `recordSwap` (:9844) stores the donor's detail on the entry (`{from,to,ts,detail}`); `undoSwap` (:13865) writes that detail back after `applySwapPrefs(back)` restores the name.
- **Records already stored without a detail** (any swap made before this build): undo restores the name only, exactly as today. On an unfrozen day the next boot rebuilds the card from the engine (the record is cleared by `clearSwap`, nothing re-applies), so it self-heals. On a frozen day the record was already pruned by `pruneSwaps` and `undoSwap` finds no `hit` and returns, as today. **No migration.** Legacy records are read the same way, one optional field, never required.
- The stored detail is for undo only. `applySessionSwaps`, the build-time `cfg.exSwapPrefs` pass and the live tap keep deriving through `_swapDetailFor`; nothing replays a stored string onto a rebuilt day.

## RR4 (second counterfactual, `swapfloor_copy2.html`): tighten the token. The row is `landmine (reverse lunge|rotational press)`, not `landmine`.

Measure: `_repFloor('Landmine rotations')` goes `null → [6,10]` on the copy; only the grammar (`N×8–12 each @ RPE`) keeps its 5 engine details and 0 swap pairs unchanged. That is a latch: a fact in the table that is false (a core rotation has no load-tracking window) held harmless by a writer it does not control. A floor is a movement property (V161, V110); the table must not carry a wrong one and rely on grammar to hide it. Literal alternation over a negative lookahead: an authored list is the truth, and a future landmine lift gets its row on entry (the §12 "tag on entry" rule). Cost accepted: one more literal.

**The class it exposes, which tightening does NOT close:** the generic `dumbbell|kettlebell|\bdb\b|\bkb\b` row already floors core and carry names (`Dumbbell renegade rows`, `Kettlebell windmill`, `Weighted 90/90 hip switch`, `Suitcase carry`) at `[5,8]` today, held out only by grammar and `_BW_KEEP_FIXED`. Pre-existing, unruled. Gatekeeper's named assertion should pin the CLASS, not the one name: across the lattice, no item with `_pattern` null changes under `_swapDetailFor`, and `Landmine rotations` is its named example. What could let the class in later: a writer that prints a `_pattern`-null item in wave grammar (a core Main), or the V162 aux swap families routing through `_swapDetailFor`.

**Undo on a day with two same-name items: in scope as an identity pin, not as a mechanism.** The forward swap already renames every same-name item (name-keyed, V102), so undo hitting every one is symmetric; the new risk is R4 writing ONE stored detail onto two items that had different details. Rule: swap then undo is byte-identical on the whole day, including a duplicated-name day. Builder's mechanism (store the item position beside the name and restore by position, name as fallback). Measure: count duplicated-name days in the lattice; if 0, the pin is a negative control, not a fix.
