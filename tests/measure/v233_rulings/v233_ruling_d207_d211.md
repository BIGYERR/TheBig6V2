## D207 — Every bike wheel parks on the dash when storage is blank. No plan face on any bike shape.

**Finding.** D205 said dash. Confirmed on all five shapes, with the reason now grounded in printed code. `_iawCommit` (:13691) writes nothing until the wheel has rested on a face other than its seed face. `iaWheelFlush` (:13700-13704) runs only a settle that is still pending; "an untouched or already settled wheel is left alone and never writes." So a plan-seeded wheel the athlete never touches stores `''` through Done. On the run `time` form that is honest: `doseDerived` substitutes `dose.mins` for `''` and prints "assuming planned", so the face and the readers agree. On bike there is no derived line, and measure's complete reader list (9 lines) shows every reader treats `''` as nothing: Progress weekly bike minutes sums with `>0`, the sessions count and `_hasLog` are truthy checks, the unmarked-day list is a truthy check. A bike wheel reading `0:45:00` over `''` is a ride the app shows and does not count. That is exactly the V182 D3 forbidden state (a face that looks logged while nothing is stored), and the run D202 exemption does not reach it.

**Per shape.**
- `time` (91,620 lattice forms; strip prints N min): dash. The plan is in the strip one line above.
- `reps_time` (24,660; strip prints R × M min): dash. There is no single planned total to seed anyway.
- null-dose Interval (12,600; no strip): dash. Nothing to seed.
- Injury cross-train `time(parsed)` (654,696 forms on injured multi-sport builds, "Easy spin, N minutes"): dash. Same emitter, same readers.
- Swapped-in bike field (300,960 run or swim days where the picker can land on bike; null dose, no strip): dash.

Implementation consequence: `iaWheelHTML('hms','log_bike_mins',e.bike_mins||'')` with no fifth argument, so no `data-plan` lands on any bike wheel. The seed-face guard then means opening a bike day never writes, whatever the stored string (D200's gate, inherited).

**Coaching argument.** The prescription owns the fixed dimension and the strip already prints it. The log captures what the watch showed. On bike the only way the app learns a ride happened is a stored number, so the wheel must start from "nothing yet", and the dash is the one face that says that. The cost, named: every dosed bike session is a throw from the dash (hours one notch to 0, minutes up to 30 rows via wrap, seconds can stay 00), two touches where the run time form needs zero for an as-planned session. Accepted.

**Deliberately not changed.** The four readers. Teaching them that blank means planned on a dosed bike day was considered and rejected: it would silently add planned minutes to every past bike day the athlete left blank, so a skipped ride would start counting as volume in Progress history, and the bike form has no derived line to tell the athlete the number is an assumption.

**Mario's call (his thumb).** Recommendation: dash on every bike shape. Counter: a plan face with the readers taught to match (the run convention made whole on bike) saves two touches per ride, at the price of reinterpreting every stored blank bike day and four reader edits that need their own measure.

## D208 — The hms parse clamps the whole face to the dial's ceiling, derived from the column maxes. This is a shared-seam change and therefore a run diff too.

**Finding.** D200 said "stored values above 599.99 clamp hours to 9 for display only". Measure shows what shipped is a column clamp, not a face clamp: `hh=Math.min(9, floor(t/3600))` then minutes and seconds carry on from `t%3600`. So stored 600 shows `9:00:00`, 601 shows `9:01:00`, and the reproduced rest-sheet sum 630.5 would show `9:30:30`. Each is an hour short, in the shape of a real time. A touch of any column would then commit 540.xx over a 630.5 store: a rewrite to a different wrong number. Reach: today's bike box has no max, and the rest sheet's "Training anyway?" move puts a summed `bike_mins` (600 + 30.5 reproduced) onto a bike day that opens the log form; every rest day on both lattices sits in a week with a movable bike day (85,680/85,680 and 191,436/191,436). After V233 the wheel itself cannot emit above 9:59:59, so new entries never exceed the ceiling; only legacy typed values and rest-sheet sums do.

**Re-ruling against D200's shipped reading, explicitly.** The `dec3` parse already clamps to the column max (150 miles shows 99). The hms parse should do the same for the face as a whole: clamp `t` to `cols[0].max*3600 + cols[1].max*60 + cols[2].max` seconds (9:59:59), computed from `_IAW_SPEC.hms.cols`, not a hand constant. A pegged face is visibly pegged. A touch then commits 599.98, the dial's ceiling, which is what a wheel's contract says it can hold. Seeding still writes nothing.

**Run side, named.** The parse is shared. The run time wheel's face changes only for a stored `run_mins` of 600 or more. Planned run minutes max 268.55 at target; no run minutes box exists on any form since V232; the rest sheet writes `run_dist`, never `run_mins`. So the run reach is a legacy value typed into a pre-V232 box, zero on the lattice. The diff hunk is one expression in `_iawParse`; gatekeeper should drive it with hand values on both kinds (600, 630.5, 599.98 all seed `9:59:59`; 599 seeds `9:59:00`; 45.5 still seeds `0:45:30`).

**`1e1` and `3,5`.** D203 accepted these as display clamps on run; the same acceptance applies on bike. After V233 no bike number box exists on the log form, so neither string can be typed there; the rest sheet uses `inputmode="numeric"` (no `e` on that keypad) and `+this.value||0`. Legacy only. Accept.

Recommendation: clamp the whole face, derived from the spec. Counter: D200 is shipped and a 630-minute rest-day bike sum is a data defect route, so a shared-seam hunk on the run form defends a value nobody legitimately stores.

Record in §12 under P-RESTWHEEL. Not this build.
- **Swim yards:** no, per D205. Nothing new in the evidence.
- **Swap erasure (reach Q3):** `setCardioSwap` run to bike erases stored `run_mins` and `run_dist`, and swapping back does not restore them. This is silent loss of watch numbers on a run day and it predates this build. It is a swap-semantics ruling (which sport's fields survive a swap), touching `persistLogFields` and run storage with g191/g221 as touchers, so it needs its own measure and a fresh coach. Record in §12 as its own item (suggest P-SWAPKEEP) and recommend it as the next quick build after V233. Not this build: bundling a run-storage hunk into a bike-form build doubles the gate surface and the blast radius.
- **`1e1` on an iOS keypad:** stays an open unknown but becomes moot on the bike form after 233.

Recommendation: V233 is the bike branch plus the shared clamp, nothing else. Counter: the swap erasure is real data loss and a one-build delay is one more week in which a mis-tap on the picker can wipe a logged run.
