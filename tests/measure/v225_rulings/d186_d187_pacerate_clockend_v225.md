## D186 — P-CLOCKEND: the block target is the last build week's pace; the taper holds it; the note names it
**Finding (pre-existing on every not-met pace goal, from V50).** `buildRunProgressionForLength` (:3629) sets `rawImprovement = gap / buildWeeks` (:3759) and `realisticTargetPace = initial − weeklyImprovement × buildWeeks` (:3772), but prints week w as `initial − weeklyImprovement × w` from w = 0 (:3781). With N build weeks there are N−1 steps between week 1 and week N, so the clock is one step off at the end, two ways:
1. Dampened (rate-capped) goals: the INT note's "target for this block" is a pace no week prints (undated 2160/2160 on V224; dated taper prints it, one step FASTER than the last build week, 6480/6480). That contradicts "intensity is held throughout" (V115/V116) and D2b-iii's rule that the note names a pace the athlete is handed (the swim side already obeys it through `_reachSplit`, :4893, D110a/D144).
2. Un-dampened (reachable) goals: the goal pace is first prescribed IN THE TAPER, or, undated, never. Printed this session: int 18-35, mile 8:00, 1.5 mi in 12:00, dated +8w → B clock `8:14 8:12 8:10 8:08 8:06 8:04 8:02 | 8:00 8:00`, last build week 8:02, taper introduces 8:00. Undated same goal, 6 weeks: `8:14 8:12 8:10 8:07 8:05 8:02`, goal 8:00 never printed.

**Coaching argument.** The taper is a primer. It holds the pace the block built and cuts the volume; it never introduces a faster target. The block target therefore IS the last build week's pace, and there is exactly one honest way to reach a goal in N build weeks: divide the gap over N−1 steps so week N lands on it. Then, when the rate caps the walk, the last build week, the taper and the note all say the same number, and when it does not, the last build week is the goal.
