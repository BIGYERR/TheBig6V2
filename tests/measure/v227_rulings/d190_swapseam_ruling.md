## Ruling

**R1. The cue is a property of two things only: the injured athlete's plan and the movement that is on the card now.** Not of the item's origin (V223 already ruled that) and not of the chain's history (new). The cue is written by exactly one function, `applyInjuryFilter`, and it is written after every hop on both paths. `_swapDetailFor` never sees it, on either path.

**R2. Strip before carry, at both hop sites.** Immediately before `_swapDetailFor` runs on a hop, the donor detail has the cue removed: the exact literal suffix, nothing else. The two hop sites are `applySwapPrefs` (:10166, the boot replay, undo and the `cfg.exSwapPrefs` build path) and `applySwapChoice` (:14290, the live tap). The literal at :8125 is hoisted into one constant that the appender and the stripper both read; this is the file's own string, not a new number. `_swapDetailFor` itself is not edited (it is D177's function and `applyAddChoice` calls it too; see scope).

**R3. Live filter after `_reRx`.** In `applySwapChoice`, after `_swapDetailFor` and after `_reRx` is computed, when `activeProg.cfg.injury` is set, the swapped item's detail is replaced by what `applyInjuryFilter` returns for `{name:to, detail}` wrapped in a throwaway section, the `_swapInjuryOK` shape (:9960), taken only when the item survives under its own name. Detail only; the name is never taken from the filter (the candidate is already legal by `_swapInjuryOK`, so it survives unrenamed).

**R4. `_reRx` compares against the stripped donor.** `_reRx = (item.detail !== _base)` where `_base` is the stripped `_wasDetail`. So the V119 "No load to add here" copy fires only when the unloadable branch moved the dose, exactly as today, and never because a cue appeared or disappeared. The three toast strings and the three branches do not change.

**R5. The boot's end-of-replay re-filter stays, unchanged.** It is the boot's only cue writer and measure proved it load-bearing. The strip in `applySwapPrefs` is the only boot-side change, and it is the same edit the live hop gets: both paths hand `_swapDetailFor` the same cue-free input, so the one filter decides the cue from the same two facts on both.

**R6. Undo unchanged.** `_undoRx` is captured from the live card by position before the rename (cued or not, as the plan decided it), and `undoSwap` writes it back. Measure's S1 already showed the 5 undo-boot rows heal once the live middle hop is cued; R2/R3 keep that.

Order inside `applySwapChoice`, for builder (one contiguous edit):
```
item.name=to;
const _wasDetail=item.detail;
const _base=<strip cue>(_wasDetail);              // R2
const _rx={};
item.detail=_swapDetailFor(to,_base,_rx);
const _reRx=(item.detail!==_base);                 // R4
if(activeProg.cfg&&activeProg.cfg.injury) item.detail=<filtered detail for {name:to,detail:item.detail}>;   // R3
```
Then the label sync, `recordSwap`, `resnapshotDayEdit`, `openDetail`, toast, all as today.

Why live == boot on every chain, including hop3+, by construction: let U_k be the cue-free chain state (`_swapDetailFor` applied k times to the stripped grid detail). The boot computes U_n and filters once. The live path computes F(U_k) at each hop; because the strip is the exact inverse of the append (the cue is a fixed suffix, appended at most once since it contains "RPE"), strip(F(U_k)) = U_k, so the next hop starts from U_k and the live card after n hops is F(U_n). Same input, same single writer, same answer. The 5 surgery-created rows vanish because the hinge and the hip_ext ends never see a cue to carry.

## Coaching argument

The sheet offers a knee athlete a goblet squat under one condition: the plan caps it at RPE 7. `swapCandidates` already asks the real filter whether the movement survives (`_swapInjuryOK`), and then throws the filtered detail away. So the condition of the offer is dropped from the card the athlete trains off, and shows up the next morning after a reboot. The plan's instruction arriving a day late is the defect; the boot card was right and the live card was short (V223 ruling, confirmed). D177's own rule finishes the thought: a swapped item is prescribed the way the engine would have prescribed it in that slot, and the engine runs the injury filter on every item it prescribes. The cue is the plan speaking about the movement on the card. A claim belongs to the item it describes (§10b: "move claims onto the item they describe"); a hinge the ankle plan does not cap must not say "hold RPE 7", and a Nordic curl must not print RPE 7 because two taps ago the athlete passed through a goblet squat. Prescription owns the fixed dimension; a prescription decided by tap history is not a prescription, it is a latch. One writer for the cue, both paths blind to it on the carry: that is the same lens rule the pool and post-filter already obey.

Doctrine: the cap itself (patterns clamped to RPE 7 under a workaround plan, the `scheme()` p-clamp for wave lifts and the appended note for fixed-detail accessories, :7966) is app doctrine already ruled, not NSW or NRC text; this ruling does not reopen it and cites no page for it.

### A. The revisit class is split off: D191 P-SWAPREVISIT, not absorbed
